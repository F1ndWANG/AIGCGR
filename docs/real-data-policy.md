# 真实数据策略

LifeRec 的目标是优先使用真实动态数据，不把本地示例数据伪装成实时数据。

## 1. 数据来源分级

| 数据类型 | 当前来源 | 是否实时 | 说明 |
|---|---|---:|---|
| 附近餐厅 | 高德 POI API | 是 | 有经纬度和 `AMAP_API_KEY` 时使用 |
| 附近景点 | 高德 POI API | 是 | 旅行推荐优先使用高德景点数据 |
| 逆地理编码 | 高德逆地理编码 API | 是 | 经纬度转城市、区县、地址 |
| 天气 | 高德天气 API | 是 | 通过城市或 adcode 获取 |
| 步行路线 | 高德步行路径规划 API | 是 | 返回真实距离、耗时和步骤 |
| 商品 | AIGC 生成商品需求 | 否 | 不声称是真实 SKU、库存或价格 |
| 用户画像 | 用户本次输入或授权数据 | 否 | 属于用户提供的个人上下文，不是外部实时数据 |
| 近期饮食 | 用户本次输入或授权数据 | 否 | 属于用户主动记录的数据 |
| 用户反馈 | 用户点击行为 | 否 | 用于后续推荐重排 |

## 2. 强约束

- 餐厅、景点、天气、路线等外部生活服务数据，优先走高德真实 API。
- 商品推荐不依赖淘宝、京东、拼多多，也不虚构购买链接。
- AIGC 商品模块只生成“应该买什么类型的东西”，例如规格、预算参考、选择标准。
- 如果某个 Provider 没有真实数据，响应中必须保留 `source`，说明是 `unavailable`、`aigc` 或 `sample-data`。
- 本地 JSON 只用于开发 fallback、测试和演示；`STRICT_REAL_DATA=true` 时不用于补推荐结果。
- 用户反馈只影响候选排序，不生成虚假地点、天气、路线或商品。

## 3. 当前真实 API

| API | 端点 |
|---|---|
| 周边地点 | `POST /api/context/nearby` |
| 关键词地点 | `POST /api/context/places/search` |
| 逆地理编码 | `GET /api/context/geocode/reverse` |
| 天气 | `GET /api/context/weather` |
| 步行路线 | `POST /api/context/route/walking` |
| 综合推荐 | `POST /api/recommend` |

## 4. 推荐接口中的真实数据行为

### 餐厅推荐

当请求包含：

```json
{
  "latitude": 31.936,
  "longitude": 118.904,
  "radius_km": 3
}
```

且已配置 `AMAP_API_KEY` 时，`/api/recommend` 会直接调用高德周边搜索获取真实餐厅 POI。

### 旅行推荐

- 有经纬度时：优先搜索附近真实景点。
- 有城市名时：优先使用高德关键词搜索该城市景点。
- 严格真实数据模式下无法获取真实数据时：返回空结果并提示配置或位置问题。

### 商品推荐

商品接口：

```text
POST /api/context/products/search
```

默认走 AIGC 商品生成。返回的是商品类型和购买建议，不是实时商品 SKU。严格真实数据模式下，如果 LLM 不可用，不会回退到本地商品样例。

## 5. 仍需注意的边界

- 高德 POI 不提供完整菜单，因此餐厅的“菜品建议”是健康选择原则，不代表该餐厅真实菜单。
- AIGC 不应生成“某平台具体链接”“实时库存”“真实折扣”等未经验证的信息。
- 用户饮食、健康目标和偏好属于本地个人数据，需要用户主动提供或授权。
